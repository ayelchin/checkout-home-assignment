# Keep payment idempotency in the MVC action filter

Status: accepted; reinstated on 2026-11-16. Supersedes ADR-0003.

Because this application has only a REST adapter and the assignment requires process-local deduplication, the endpoint-specific MVC action filter owns the atomic merchant/key map and replays the stored MVC action result. The key alone identifies the attempt; request parameters are not compared or retained. Matching in-flight requests await the winning action, while GET can retrieve the safe InProgress payment persisted by the use case. The use case and payment repository own payment persistence and completion, not idempotency coordination. Basic body validation occurs before the action filter; invalid or blank keys are independent attempts, and oversized keys fail before reservation. If validation throws before bank processing, its filter reservation is released and the stored payment remains InProgress. If bank processing may have started, the bank service returns Declined/BankUnavailable and the use case stores that outcome and the filter keeps the key bound to the response. Filter and payment state are process-local and lost on restart. Revisit this decision if another transport adapter or durable coordination is introduced.
